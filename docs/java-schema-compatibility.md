# Schema compatibility: Alembic → JPA

The Java backend must attach to the **same PostgreSQL schema** the Python backend
already owns. This document is the authoritative mapping.

It was produced by running `alembic upgrade head` against an empty PostgreSQL 16
database and introspecting `information_schema` / `pg_catalog` — not by reading the
migration files. What follows is what the database actually contains at Alembic
revision `008_exercise_scope_indexes`.

**Hibernate runs with `ddl-auto=validate`. It never generates or alters DDL.**

## Summary

- 12 application tables + `alembic_version`
- 5 native PostgreSQL enum types
- 39 seeded rows in `exercises`
- All UUID primary keys, all `gen_random_uuid()` defaults **except `refresh_tokens.id`**
- All user-owned tables cascade on user delete at the **database** level

---

## Type mapping rules

| PostgreSQL | Java | Notes |
|---|---|---|
| `uuid` | `java.util.UUID` | `@GeneratedValue` only where a DB default exists |
| `timestamp with time zone` | `java.time.Instant` | `Instant.toString()` emits the trailing `Z` the current API returns. `OffsetDateTime` would emit `+00:00` and break the contract |
| `date` | `java.time.LocalDate` | serialises as `YYYY-MM-DD` |
| `double precision` | `Double` | **not `BigDecimal`** — see below |
| `integer` | `Integer` | |
| `boolean` | `Boolean` (primitive `boolean` where `NOT NULL`) | |
| `character varying(n)` | `String` + `@Column(length = n)` | |
| `USER-DEFINED` (native enum) | Java `enum` + `PgEnumUserType` + `columnDefinition` | NAMED_ENUM was measured and **rejected** — see below |

### Why `Double` and not `BigDecimal`

The migration brief suggests evaluating `BigDecimal` for weights and nutrition values.
Having inspected the columns, the answer is **no**, and the reasoning is worth stating:

1. Every numeric measure (`weight_kg`, `protein_g`, `body_fat_pct`, `height_cm`, …) is
   `double precision` in PostgreSQL. `BigDecimal` would not add precision that the
   column can store — it would only add a conversion step.
2. It would change the wire format. The API currently returns `"weight_kg": 45.0`.
   Preserving that exactly is a hard requirement, and `Double` does it natively.
3. There is no money and no medical dosing in this schema. The analytics engine
   already compares floats through an explicit epsilon and a 2% threshold — orders of
   magnitude above float error at gym-weight scale (documented in
   [adaptive-training.md](adaptive-training.md) §6).

Changing the storage type is a schema redesign, which this migration explicitly is not.
If decimal precision is ever wanted, it should be its own migration with its own
rationale, after the Java cutover.

## Tables

### `users`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | uuid | NOT NULL | `gen_random_uuid()` |
| `email` | varchar(255) | NOT NULL | — |
| `password_hash` | varchar(255) | **NULL** | — |
| `role` | `user_role` | NOT NULL | `'user'` |
| `email_verified` | boolean | NOT NULL | `false` |
| `is_active` | boolean | NOT NULL | `true` |
| `created_at` | timestamptz | NOT NULL | `now()` |
| `updated_at` | timestamptz | NOT NULL | `now()` |
| `deleted_at` | timestamptz | NULL | — |

Constraints: `PK(id)`, `UNIQUE(email)`. Indexes: `ix_users_email`.

Notes for Java:
- `password_hash` is **nullable** — the Python code treats a null hash as an
  OAuth-only account (login rejected, password reset silently no-ops). Preserve this.
- `updated_at` is maintained by SQLAlchemy's `onupdate`, **not** a database trigger.
  Hibernate must set it with `@UpdateTimestamp`, or the column silently stops updating.
- `is_active` + `deleted_at` together form a soft delete. Every authentication path
  checks `is_active AND deleted_at IS NULL`.

### `refresh_tokens`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | uuid | NOT NULL | **none** |
| `user_id` | uuid | NOT NULL | — |
| `token_hash` | varchar(255) | NOT NULL | — |
| `expires_at` | timestamptz | NOT NULL | — |
| `revoked_at` | timestamptz | NULL | — |
| `created_at` | timestamptz | NOT NULL | `now()` |
| `user_agent` | varchar(512) | NULL | — |
| `ip_address` | varchar(45) | NULL | — |

Constraints: `PK(id)`, `FK(user_id) → users ON DELETE CASCADE`.
Indexes: `ix_refresh_tokens_user_id`, `ix_refresh_tokens_expires (expires_at) WHERE revoked_at IS NULL`.

**The single most important row in this document:** `refresh_tokens.id` has *no*
database default because it is not generated by the database. It is the refresh JWT's
`jti` claim, assigned in application code. Java must do the same — `@Id` with **no**
`@GeneratedValue`, the UUID parsed from the minted token's `jti`. Letting Hibernate
generate it would break refresh entirely, because lookup is `findById(jti)`.

### `alembic_version`

Single `varchar(32)` column holding `008_exercise_scope_indexes`.

**Do not drop this table during the migration.** It is the record of where the Python
schema stopped and the rollback anchor if the Java cutover has to be reverted. It can
be removed in a later cleanup, once Python is retired for good.

## Enum types

Native PostgreSQL enums, all lowercase on the wire:

| Type | Values |
|---|---|
| `user_role` | `user`, `admin` |
| `exercise_category` | `strength`, `cardio`, `mobility`, `other` |
| `goal_status` | `active`, `achieved`, `abandoned` |
| `profile_sex` | `male`, `female`, `unspecified` |
| `profile_activity_level` | `sedentary`, `light`, `moderate`, `active`, `very_active` |

Java enum constants are conventionally uppercase. The JSON must stay lowercase, so each
enum carries an explicit value:

```java
public enum ExerciseCategory {
    STRENGTH("strength"), CARDIO("cardio"), MOBILITY("mobility"), OTHER("other");
    private final String value;
    @JsonValue public String getValue() { return value; }
}
```

Persistence is the harder half, and the obvious answers do not work. Measured in
Phase 0.5 against Testcontainers PostgreSQL 16:

| Mapping | Result |
|---|---|
| `@Enumerated(EnumType.STRING)` alone | write fails: `column is of type user_role but expression is of type character varying` |
| `@JdbcTypeCode(SqlTypes.NAMED_ENUM)` | **validate passes**, then every insert fails: `invalid input value for enum user_role: "ADMIN"` — it binds `Enum.name()`, which is uppercase |
| `AttributeConverter` + `SqlTypes.OTHER` | context will not start: `no type mapping for SqlTypes code 1111 (OTHER)` |
| Custom `UserType` alone | same `MappingException` — Hibernate still needs a SQL type name |
| **`PgEnumUserType` + `@Column(columnDefinition = "user_role")`** | **works** — validate, insert, read, update, derived queries and JPQL |

The NAMED_ENUM result is the dangerous one: schema validation passes because the
validator compares column types and never exercises a bind, so the mapping looks correct
at startup and fails on the first write.

The working mapping:

```java
@Type(UserRoleType.class)
@Column(name = "role", nullable = false, columnDefinition = "user_role")
private UserRole role = UserRole.USER;
```

`PgEnumUserType` binds `getValue()` as `Types.OTHER` so PostgreSQL coerces the untyped
label into the enum — which is also what makes it work as a query parameter, since
PostgreSQL will not compare `user_role = character varying`. `columnDefinition` supplies
the type name Hibernate needs for JDBC type code 1111.

One shared base class covers all five enum types; each needs a three-line subclass.

## Cascade policy

Every `ON DELETE CASCADE` above is a **database** constraint, already enforced.

JPA must not duplicate it. Adding `cascade = CascadeType.ALL` from `User` to every child
collection would make Hibernate issue its own `DELETE` storm on user removal — slower
than, and redundant with, what PostgreSQL already does correctly. The one legitimate
JPA cascade is `Workout → WorkoutExercise`, because the service replaces that collection
wholesale on update.

## Verification

Phase 2 onward, the Testcontainers PostgreSQL container is provisioned from the Flyway
baseline (see the migration plan's Flyway section), and every integration test run
boots the context with `ddl-auto=validate`. A drift between a JPA entity and this schema
therefore fails the build rather than surfacing in production.
